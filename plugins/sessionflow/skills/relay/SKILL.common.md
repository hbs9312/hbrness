# Relay Skill — 바통 모델 페이즈 러너

긴 작업을 **페이즈로 쪼개고, 페이즈마다 서브에이전트를 새로 띄워 바통을 넘긴다.** 오케스트레이터(너)는 끝까지 살아남아 계획·디스패치·핸드오프 작성만 하고, 실제 작업은 매번 컨텍스트가 0인 서브에이전트가 한다.

```
계획 수립 → [페이즈 N: 서브에이전트 구현 → 리뷰(선택) → 리포트 수령 → 핸드오프 작성] → 다음 페이즈 → … → 끝
              ↑ 여기만 매번 새 컨텍스트                      ↑ 오케스트레이터는 계속 살아 있음
```

## phase-run / phase-loop 과 뭐가 다른가

| | phase-run · phase-loop | relay |
|---|---|---|
| 컨텍스트 리셋 | 자기 pane 에 `/clear` 키를 되쏨 | 페이즈마다 서브에이전트 신규 |
| 터미널 의존 | tmux 필요 | 없음 |
| 페이즈 실패 | 되돌릴 수 없음(컨텍스트 소실) | 다시 디스패치하면 끝 |
| 병렬 페이즈 | 불가 | 가능 |
| 누적 위험 | 없음 | **오케스트레이터가 규율을 깨면 발생** |

마지막 줄이 이 스킬의 전부다. 아래 불변 원칙은 그 누적을 막기 위한 것이고, `relay.sh metrics` 가 실제로 얼마나 붙었는지 숫자로 보여준다.

## 불변 원칙 (반드시 지킬 것)

1. **오케스트레이터는 코드를 직접 조사하지 않는다.** 파일을 열거나, grep 하거나, 테스트를 돌려 원인을 파지 않는다. 그 순간 이 모델의 유일한 장점이 사라진다. 네가 쓰는 툴은 계획 수립, 서브에이전트 디스패치, `relay.sh` 호출, 사용자에게 질문, 핸드오프 작성뿐이다.
2. **서브에이전트가 실패해도 네가 파지 않는다.** 실패 리포트를 받으면 **진단 전용 서브에이전트**를 새로 띄운다. 진단 결과도 리포트로 받는다.
3. **핸드오프에 코드를 설명하지 않는다.** 다음 서브에이전트는 레포를 자기가 다시 읽는다. 네가 넘기는 건 *의도와 제약*이지 *코드의 요약*이 아니다. 요약의 요약이 쌓이는 게 이 모델의 유일한 실패 경로다.
4. **핸드오프는 되돌릴 수 없다.** 다음 서브에이전트는 컨텍스트가 0이라, 핸드오프에 없는 것은 영영 모른다. `relay.sh handoff` 가 필수 섹션을 검사하지만, 검사를 통과했다고 내용이 충분한 건 아니다.
5. **사용자 확인이 필요한 일은 네가 묻는다.** 서브에이전트는 사용자에게 못 묻는다. 리포트의 `## 막힌 것 / 판단 필요` 에 올라온 것은 네가 사용자에게 묻고, 답을 다음 디스패치 프롬프트에 실어 보낸다.
6. **커밋은 `--mode auto` 가 아니면 사용자 확인을 받는다.** 서브에이전트에게 커밋 권한을 주지 않는 게 기본이다. 커밋이 필요하면 리포트로 올라오게 하고 네가 처리한다.
7. **서브에이전트에게 주는 프롬프트는 길게 쓴다.** 받는 쪽은 네 컨텍스트를 못 본다. 파일 경로, 정확한 식별자, 실행할 명령, 이미 실패한 시도, 판단 근거를 전부 적는다. 사람에게 하는 설명의 간결함 규칙은 여기 적용하지 않는다.

## 인자 디스패치

| 첫 토큰 | 동작 |
|---|---|
| (없음) 또는 자연어 계획 | **START** — 계획을 세우고 `init` |
| `continue` | 현재 페이즈 이어가기 |
| `status` / `metrics` / `pause` / `resume` / `stop` / `reset` | `relay.sh` 에 그대로 위임하고 출력만 전달 |

```bash
bash "${SKILL_DIR}/scripts/relay.sh" <status|metrics|pause|resume|stop|reset>
```

---

## START — 계획 세우기

1. `bash "${SKILL_DIR}/scripts/relay.sh" status` 로 진행 중인 게 있는지 본다. 있으면 이어갈지 물어본다.
2. 사용자의 요구를 페이즈로 쪼갠다. **여기서만 코드를 봐도 된다** — 계획을 세우려면 현황 파악이 필요하다. 다만 이 단계에서 읽은 내용을 이후 페이즈 판단에 쓰지 말고, 계획서에 적어 넘긴다.
3. 페이즈를 나누는 기준: **앞 페이즈의 결과 위에 다음이 얹히는가.** 독립적이면 굳이 나누지 말고 한 페이즈에서 병렬로 처리한다. 3~6개가 보통이고, 하나가 서브에이전트 한 번에 안 끝날 것 같으면 더 쪼갠다.
4. 계획서를 파일로 쓴다. 각 페이즈는 `## Phase N — 제목` 헤딩이어야 한다(스크립트가 이걸로 페이즈 수를 센다).

```markdown
# <작업 이름>

## 목표
<끝났을 때 무엇이 참이어야 하는지. 사용자 말로.>

## 제약
<건드리면 안 되는 것, 지켜야 할 관례, 이미 정해진 결정>

## Phase 1 — <제목>
- 할 일:
- 끝났다고 볼 조건:
- 이 페이즈가 만드는 것(다음 페이즈가 딛고 설 것):

## Phase 2 — <제목>
...
```

5. 사용자에게 계획을 보이고 **한 번만** 확인받는다. 이후 경계마다 차단형 확인은 하지 않는다(커밋 확인 제외).
6. 시작한다:

```bash
bash "${SKILL_DIR}/scripts/relay.sh" init --plan <계획파일> --review <none|cleanroom|xreview|both> --mode <auto|confirm>
```

`--review` 는 페이즈마다 리뷰를 끼울지다. `cleanroom` 은 같은 모델의 새 서브에이전트가 **구현 맥락 없이** diff 만 보고 리뷰한다(빠름, 맹점 공유). `xreview` 는 반대편 provider CLI 가 백그라운드에서 리뷰한다(느림, 다른 모델의 눈). `both` 는 둘 다.

## 페이즈 루프

각 페이즈마다 이 순서를 돈다. `relay.sh status` 로 지금 몇 번째인지 확인하고 시작한다.

### 1. 디스패치

서브에이전트 하나를 띄운다. 프롬프트에 **반드시** 넣는다:

- 계획서 경로와 이번 페이즈 번호 (`PLAN.md` 의 `## Phase N` 을 읽으라고 지시)
- 직전 핸드오프 경로 (`relay.sh paths` 의 `handoff`). 1페이즈면 없다고 명시.
- **레포를 직접 읽으라는 지시.** 핸드오프가 코드를 설명하지 않는다는 걸 알려준다.
- 리포트 형식(아래)과 "리포트로만 보고하라"는 지시
- 권한 경계: 커밋·push·PR 금지(`--mode auto` 가 아니면), 레포 밖 수정 금지
- 사용자에게 물을 수 없으니 판단이 필요하면 리포트의 해당 칸에 올리라는 지시

### 2. 리포트 수령

서브에이전트는 이 형식으로 돌려준다. 형식이 깨졌으면 다시 정리해 달라고 한 번 요청한다 — 네가 읽고 재구성하지 않는다.

```markdown
## 한 일
## 변경한 파일          ← 경로 목록. 파일별 한 줄 설명
## 실행한 명령과 결과    ← 명령과 출력 원문. 실패한 것도 그대로
## 남긴 것              ← 안 한 것, 왜 안 했는지
## 다음 페이즈가 알아야 할 사실
## 막힌 것 / 판단 필요   ← 사용자 결정이 필요한 것. 없으면 "없음"
## 계획 수정 제안        ← 해보니 계획이 틀렸으면. 없으면 "없음"
```

받으면 바로 보관한다:

```bash
bash "${SKILL_DIR}/scripts/relay.sh" report <리포트파일>
```

`## 계획 수정 제안` 이 비어 있지 않으면 **남은 페이즈를 다시 짜고** 사용자에게 알린다. 이게 오케스트레이터가 코드를 안 보면서도 계획 오류를 잡는 유일한 경로다.

### 3. 리뷰 (`--review` 가 `none` 이 아닐 때)

**클린룸** — 새 서브에이전트에 diff 와 이번 페이즈의 목표만 준다. **구현자 리포트는 주지 않는다.** 구현 이유를 모르는 눈을 사는 게 목적이고, 리포트를 주면 그 목적이 사라진다. 리뷰 대상은 **이번 페이즈의 diff** 로 한정한다(브랜치 전체로 잡으면 지난 페이즈 findings 가 다시 올라온다).

**xreview** — `/xreview:live --scope working` 로 띄우고 turn 을 끝낸다. 완료 핑이 오면 결과 파일을 읽는다. 비동기이므로 그동안 다른 페이즈를 진행하지 않는다.

findings 는 severity 로 받는다:

```markdown
## critical   ← 지금 고친다
## warning    ← 지금 고치거나 다음 페이즈 핸드오프에 넘긴다
## info       ← 읽지 말고 followup 으로 민다
```

`## info` 는 **읽지 않는다.** `sessionflow:followup` 으로 그대로 넘긴다. 여기서 컨텍스트가 제일 많이 샌다.

```bash
bash "${SKILL_DIR}/scripts/relay.sh" review <findings파일>
```

고칠 게 있으면 **fix 전용 서브에이전트**를 새로 띄운다(구현자는 이미 끝나서 컨텍스트가 없다). diff + findings + 이번 페이즈 목표를 준다. fix 결과도 리포트로 받아 `report` 로 보관한다.

### 4. 핸드오프 작성

**네가 직접 쓴다.** 리포트를 그대로 복사하지 말고, 다음 서브에이전트가 알아야 할 것만 옮긴다.

```markdown
## 지금 상태
<브랜치, 워킹트리, 어디까지 됐는지. 사실만.>

## 다음 페이즈가 해야 할 것
<계획서의 Phase N+1 을 이번 결과에 비추어 구체화한 것>

## 건드리면 안 되는 것
<이번 페이즈가 세운 전제, 깨면 안 되는 것>

## 이미 시도했다 실패한 것
<같은 벽에 다시 부딪히지 않게. 리포트의 실패한 명령과 출력 포함>

## 열린 질문
<아직 안 정해진 것. 사용자에게 물어 답이 나왔으면 답도 같이.>
```

코드를 설명하지 않는다. "`api/orders/repo.ts` 의 `findByStatus` 가 새 컬럼을 읽도록 바뀌었다" 는 쓰지 말고, "주문 조회 경로는 이미 new_status 를 읽는다. 다시 손대지 말 것" 이라고 쓴다. 전자는 다음 에이전트가 파일을 열면 알 수 있고, 후자는 열어도 모른다.

```bash
bash "${SKILL_DIR}/scripts/relay.sh" handoff <핸드오프파일>
```

필수 섹션이 빠지면 거절한다. 채워서 다시 부른다.

### 5. 전진

```bash
bash "${SKILL_DIR}/scripts/relay.sh" advance
```

사용자에게 한 줄 보고하고 다음 페이즈로 간다. 마지막 페이즈면 `advance` 가 알려준다.

## 끝낼 때

```bash
bash "${SKILL_DIR}/scripts/relay.sh" metrics
bash "${SKILL_DIR}/scripts/relay.sh" stop
```

`metrics` 는 페이즈별로 리포트·리뷰·핸드오프가 몇 토큰이었는지와 합계를 낸다. 이게 **오케스트레이터가 읽은 양의 하한**이다 — 네 자신의 툴 호출과 판단 턴은 안 세어졌으니 실제는 더 크다. 사용자에게 이 숫자를 그대로 보여주고, 불변 원칙을 어긴 지점이 있었으면(직접 파일을 열었다든가) 그것도 같이 밝힌다.

## 가이드라인 (너 = LLM)

- 페이즈 사이에 사용자가 끼어들면 그대로 받는다. 루프는 `pause` 로 멈춘다.
- 서브에이전트 리포트를 재해석·축약해서 사용자에게 전달하지 않는다. 요약이 필요하면 원문 위치를 같이 준다.
- 독립적인 페이즈는 굳이 순서대로 돌리지 말고 동시에 디스패치한다. 그게 이 모델이 phase-loop 보다 나은 이유 중 하나다.
- 핸드오프를 쓰다가 "이걸 확인하려면 파일을 열어봐야겠는데" 싶으면, 그건 리포트 형식이 부족한 것이다. 열지 말고 서브에이전트에게 되물어라.
